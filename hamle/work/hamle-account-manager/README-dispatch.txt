HAMLE INTERNAL DISPATCH BOUNDARY — OFFLINE ADAPTER INTERFACE

dispatch.py has no CLI, credential access or automatic retry. It remains outside
worker.py review mode. Only explicit worker --mode dispatch --proposal-id ...
wires the reviewed BusinessWriters adapter after exact approval/control gates.
No live business effect was performed by implementation or offline tests.

API:
  dispatch_approved(store, proposal_id,
      capture=..., check_basecamp=..., create_task=..., read_task=...,
      send_reply=..., read_reply=..., clock=aware_datetime_callable)
Each writer(exact_approved_payload, before_post=callback) returns {provider_id:
string} from the real provider acknowledgement. The mandatory callback must run
exactly once after authentication/preflight and immediately before the POST.
Each reader(provider_id, exact_approved_payload)
returns {provider_id: same, identity_verified: true,
         matches_approved_payload: true} only after real provider readback.
These booleans are not generated by this module: a trusted adapter must check
actual identity, destination and exact created content. No raw response logging.

Every action requires exact authenticated human approval of its purpose, whole
payload hash and control generation. routine_execution accepts routine_request
with escalation owner=none only. V3 also accepts internal_coordination_only for
complaint_strategy with owner=cansu_and_ahmet, solely for the same fixed internal
task and Ahmet reply described below. Its approval must persist
escalation_status=open, decision_authorized=false and production_authorized=false.
Strategy classification and the original model proposal are never rewritten.
The coordination reply/task does not resolve escalation or authorize strategy,
production, commercial decisions, customer messages or social planning.
It does not claim that Cansu or Özge was consulted. V6 permits Cansu's address
only because it was read from Ahmet's actual latest CC and the user explicitly
requested that current CC recipients be preserved. Özge's address is unknown.
Legacy/purposeless approval remains routine only; it cannot be upgraded to
coordination. A repeated approval never refreshes its five-minute validity.
Missing questions may remain in the approved reply/task; they do not authorize
inventing answers. Initial reply is Hamle->Ahmet, no CC; task account5898865,
project49184053, verified todo_parent_id/type (Todoset or Todolist), assigned to
Hamle53358100, no due-date promise. A Todoset ID is never treated as a Todolist.

Task first -> exact task readback -> reply -> exact reply readback.
If task is unknown, leased, rejected or not yet verified, no mail follows.
Before each NEW write: claim canonical action ID with a 60-second lease, then
the writer finishes authentication/preflight. Its final before_post callback
recaptures actual source/body hash, calculates the SAME composite fingerprint
as worker._capture, verifies current RFC headers and Basecamp private target,
rechecks control/generation/budget/approval, and commits begin_dispatch. Only
then may the adapter POST once. Expired lease/stop during preflight blocks POST.
Preflight/callback failure retains the canonical reservation without a retry.
No provider API is inside a Firestore transaction. A stop between queued actions
blocks the next write. A request already begun at the provider may complete.

Receipt or readback failure never causes a repeated create/send. Unknown write
is held. An accepted/verified action can only be read again by its provider ID,
not re-created. This matters after a reply: the latest mailbox message may now
be Hamle's own expected send, so existing receipt reconciliation does not try to
treat it as a fresh Ahmet request. Readback failure remains recoverable through
another read; it is not resend permission. Repeated successful dispatch performs
receipt reads only and reports new_write_count=0.

V6 continuation: bind_verified_work derives the immutable thread/task link only
from the original verified task and mail receipts. Follow-up proposals contain
work+comment, never task. Dispatch uses create_comment/read_comment and
read_task_status callbacks: existing-task comment -> exact readback -> reply ->
exact readback -> complete_followup. create_task is never called in this branch.
Each write rechecks the original root, latest source, current To/CC, exact work
reference and the active incomplete task's semantic fingerprint. updated_at
alone is excluded because posting our own comment changes it. Current Cansu CC
is preserved; historical CC and Hamle's own address are not added. Unknown
recipients are held for scope verification, not silently discarded.
Open Cansu/Ahmet escalation remains open even if the continuation is classified
routine. New escalation on a previously routine work is held pending an explicit
transition implementation. One unresolved follow-up per work and immutable
message deduplication prevent multiple model attempts or second tasks. A
verified replay performs only receipt reads and does not increment revision.

Model generation is not called here. No customer action is permitted and E04 is
not solved. The full proposal, every destination and the explicit approval
purpose must be visible in the authenticated control panel. Preparing V3 is not
human approval of the live draft. V3 purpose changes make no new model call.

Offline initial tests (19 cases) use injected providers: task-before-mail, repeated
receipt-only reconciliation, stop, task/mail unknown outcomes, readback recovery,
changed source, expired approval, missing approval and commercial escalation.
The final POST callback is tested for stop, lease expiry and missing invocation.
Coordination cases cover explicit purpose, open escalation and unchanged short
approval expiry. Eight added continuation cases exercise real worker/store/
dispatch composition, unknown comments, read-only recovery, recipient changes,
closed tasks, stable semantic status and zero-write repeated completion.
The complete V6 offline suite passed 247 tests. See the separately saved V6
validation and cloud execution evidence; older V3/V5 records remain historical.
This does not substitute for cloud persistence or actual provider write/readback
acceptance. Deadline/budget and live authorized writes still require root checks.
